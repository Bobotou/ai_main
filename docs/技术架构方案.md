## 1. 总体架构

产品形态为 **Web SPA + 后端服务 + 邮件网关 + AI 管道** 四层:

```
┌─────────────────────────────────────────────────────────┐
│  前端 SPA(React + TypeScript)                          │
│  列表/阅读/写信/AI 面板/设置                              │
└───────────────┬─────────────────────────────────────────┘
                │ HTTPS (REST + WebSocket)
┌───────────────▼─────────────────────────────────────────┐
│  API 网关层 (NestJS / FastAPI)                           │
│  认证鉴权 · 会话管理 · REST API · WS 推送                 │
├─────────────────────────────────────────────────────────┤
│  核心域服务                                               │
│  ├─ 账号服务(凭据加密、IMAP/SMTP 配置)                   │
│  ├─ 邮件服务(读信/写信/会话聚合/标签)                     │
│  ├─ 调度服务(定时发送、跟进提醒、同步节拍)                 │
│  ├─ 搜索服务(全文索引 + 语义检索)                         │
│  └─ AI 服务(统一 LLM 网关:摘要/分类/代笔/抽取…)           │
├─────────────────────────────────────────────────────────┤
│  后台工作进程 (Worker,消息队列驱动)                       │
│  ├─ 邮件同步引擎(IMAP IDLE / 轮询 → 解析 → 入库 → 触发AI) │
│  ├─ AI 任务管道(摘要、分类、embedding、信息抽取)          │
│  └─ 定时发送执行器                                        │
├─────────────────────────────────────────────────────────┤
│  存储                                                    │
│  PostgreSQL(结构化) · 对象存储(附件/原始邮件 .eml)       │
│  Meilisearch(全文) · pgvector(向量) · Redis(队列/缓存)  │
└─────────────────────────────────────────────────────────┘
                │
        用户邮箱的 IMAP / SMTP / OAuth(Gmail、Outlook…)
                │
                ▼  LLM API(OpenAI 兼容协议,可换 DeepSeek/GLM/本地模型)
```

设计要点:

1. **邮箱只是数据源**:产品不做 MTA,所有收发通过用户邮箱的 IMAP/SMTP 完成,自身无需域名与 MX。
2. **队列驱动**:同步、AI 生成、定时发送全部经消息队列异步执行,LLM 调用慢且可能失败,必须与请求-响应链路解耦。
3. **AI 网关统一收口**:所有 LLM 调用走一个内部 AI 服务,便于做脱敏、缓存、限流、成本统计与模型切换(这是产品「AI 可关闭、可审计」需求的技术落点)。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React 18 + TypeScript + Vite + Tailwind CSS + TanStack Query + TipTap(富文本) | 生态成熟;TipTap 对邮件 HTML 编辑与 sanitize 支持好 |
| 后端 | **NestJS (Node.js)**(备选 FastAPI) | 与前端同语言;imapflow、nodemailer 等 SMTP/IMAP 库成熟且活跃 |
| IMAP/SMTP | imapflow(收)/ nodemailer(发) | imapflow 支持完整的 IDLE、CONDSTORE 增量同步 |
| 数据库 | PostgreSQL 16 + pgvector | 结构化数据与向量统一在一个库,MVP 阶段免独立向量库 |
| 全文检索 | Meilisearch | 轻量、中文分词(可配 jieba)、毫秒级响应,比 ES 运维成本低一个量级 |
| 队列/缓存 | Redis + BullMQ | 与 NestJS 同生态,支持延时任务(定时发送天然是延时队列) |
| 对象存储 | 本地磁盘(MVP)→ S3 兼容(演进) | 附件与原始 .eml |
| LLM | OpenAI 兼容协议,默认接 DeepSeek/GLM 等,预留本地 Ollama 通道 | 摘要/分类/代笔用通用对话模型;embedding 用独立轻量模型 |
| 部署 | Docker Compose(单机自托管友好) | 目标用户含自托管人群 |

## 3. 数据模型(核心表)

```sql

users(id, email, password_hash, totp_secret, created_at)
mailbox_accounts(id, user_id,            -- 用户接入的每个邮箱账号
  address, provider,            -- gmail / qq / custom
  auth_type,                    -- password | oauth2
  imap_host, imap_port, imap_tls,
  smtp_host, smtp_port, smtp_tls,

  last_sync_uidvalidity, last_sync_uid, sync_state_json)

-- 邮件

  thread_id,                    -- 会话聚合(按 normalized subject + participants)

  sent_at, size_bytes, is_read, is_starred,
  ai_category,                  -- important/notification/marketing/social/other

  raw_eml_key,                  -- 对象存储中的原始邮件

  created_at, updated_at)

attachments(id, message_id, filename, mime_type, size_bytes, object_key,
  is_inline, content_id)

message_labels(message_id, label_id)

threads(id, user_id, subject_normalized, participants_hash,
  last_message_at, message_count)

-- 定时与规则

  scheduled_at, status,         -- pending/sent/failed/cancelled
  retry_count, last_error, sent_message_id)

  conditions_json, actions_json, is_active, hit_count)

-- AI 域

  status, prompt_tokens, completion_tokens, cost, model, error, created_at)

extracted_entities(id, message_id, entity_type,  -- event/task/bill/parcel/otp
  payload_json, confidence, action_taken)

  due_at, status)

  frequency_per_week, last_seen_at, status)      -- active/unsubscribed/auto_archived
ai_audit_log(id, user_id, message_id, capability, action, decided_by, created_at)
                                         -- decided_by: user | ai_auto
```

## 4. 邮件同步引擎

同步是整个产品的地基,设计如下:

1. **全量首同步**:账号接入后拉取全部邮件头 + 正文(上限可配,如最近 2 年/5 万封),存原始 .eml 于对象存储,解析入库。过程中前端显示进度条。
2. **增量同步**:
   - 支持 IDLE 的服务器:每账号保持一条 IMAP IDLE 长连接,新邮件秒级感知;
   - 不支持/超时后降级为轮询(收件箱 1~2 分钟,其他文件夹 15 分钟)。
   - 使用 `UIDVALIDITY + UID` 游标与 CONDSTORE,只拉增量,处理服务器端移动/删除(对账后打墓碑标记,而非物理删)。
3. **解析管道**:`mailparser` 解析 MIME → HTML 经 `sanitize-html` 白名单清洗(防 XSS,剥离 script/iframe,默认拦截远程图片)→ 纯文本用于索引与 LLM。
4. **发送**:`nodemailer` 经用户 SMTP 发送;发送成功后把该邮件写入已发送并回拉同步游标;定时发送 = BullMQ 延时任务,到点入发送执行器,失败指数退避重试 3 次后标记 failed 并通知用户(对应 PRD §4.2)。

## 5. AI 管道设计

### 5.1 任务流

新邮件入库后,Worker 按队列依次执行(失败不影响邮件本身可用):

```
message inserted
  → [P0 队列] classify(分类+优先级) → summarize(摘要/列表摘要行)
  → [P0 队列] embed → 写入 pgvector
  → [P1 队列] extract(日程/任务/账单/快递/验证码抽取)
  → [P1 队列] 营销邮件 → subscriptions 聚合
```

写侧能力(代笔、语气调整、回复建议、自然语言搜索解析)为同步/准同步调用,经 AI 网关限流。

### 5.2 AI 网关职责

对应 PRD 的隐私与可审计需求,AI 网关统一实现:

1. **脱敏**:发送前剥离附件、图片、签名块;可选正则掩码验证码/手机号/证件号;
2. **缓存**:`hash(model + prompt + content)` 命中 ai_cache 直接返回,邮件摘要类请求重复率低但改写/翻译类命中率高;
3. **预算与限流**:按用户/天设置 token 预算,超限降级(如只对新到达邮件生成摘要);
4. **模型路由**:按 job_type 配置不同模型(分类可用便宜小模型,代笔用强模型),OpenAI 兼容协议一键切换;
5. **审计**:每次调用写 ai_jobs + ai_audit_log,设置页的「AI 使用统计/审计」直接读这两张表。

### 5.3 搜索实现

- **P0 全文**:解析入索引时同步写 Meilisearch(中文分词),组合筛选由前端传 filter 表达式;
- **P1 自然语言搜索**:两段式——LLM 把查询解析为结构化条件(JSON:sender/time/has_attachment/keywords)+ 语义向量,然后 `结构化过滤 ∩ pgvector 相似度排序`,并让 LLM 生成一句结果解释;
- **P2 对话问答**:标准 RAG——query 向量召回 top-k 邮件片段 → LLM 带引用生成答案,答案附来源邮件链接跳转。

### 5.4 反馈回流

用户纠正 AI 分类(把「营销」改标「重要」)写入反馈表,用于:(a) 立即生效的同 sender 局部规则;(b) 定期用纠错样本优化分类 prompt(few-shot 注入)。


- 实时性:WebSocket 推送新邮件到达、同步进度、AI 任务完成事件(摘要异步生成后前端局部刷新,不整页轮询)。

- 响应式布局,窄屏降为「列表/详情」双页切换。

## 8. 安全与隐私实现

1. **凭据加密**:每用户派生数据密钥(由主密钥 HKDF 派生),邮箱授权码/OAuth token 以 AES-256-GCM 加密入库;主密钥来自环境变量或 KMS,数据库泄露不等于凭据泄露。凭据仅在同步/发送 Worker 内存中短暂解密,任何日志禁打。
2. **传输**:全站 HTTPS;IMAP/SMTP 强制 TLS。
3. **LLM 边界**:仅脱敏后的正文文本出站;AI 功能总开关在网关层硬拦截,关闭后零调用;第三方 LLM 供应商可配置(含自托管 Ollama),文档明示各供应商的数据政策。
4. **攻击面收敛**:邮件 HTML 双重沙箱、远程图片默认拦截(防追踪)、链接代理检测(钓鱼警示的「不直接打开原链」选项)。
5. **删除即删净**:删账号级联删除对象存储中的 .eml、附件、向量与缓存,并提供全量导出(JSON + .eml 打包)。

## 9. 部署与可观测

- **MVP**:单机 Docker Compose:`web(nginx+静态) / api / worker / postgres+pgvector / redis / meilisearch / minio`。个人自托管一条 `docker compose up` 可跑。
- 配置全部走环境变量(.env.example 全量注释)。
- 可观测:结构化日志(pino)+ 基础指标(队列深度、同步延迟、AI token/成本看板复用 ai_jobs 表)。
- LLM 成本护栏:ai_jobs 按用户/天聚合,超预算自动降级策略见 §5.2。

## 11. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 各邮箱 IMAP 兼容性参差(QQ 授权码、Gmail XOAUTH2、部分服务器无 IDLE) | mail-core 做成独立可测库,建立真实服务器兼容矩阵;OAuth 在 M2 补齐 |
| LLM 成本随邮件量线性上涨 | 分类/摘要用小模型 + 缓存 + 预算降级;历史邮件 AI 处理按需触发而非全量预处理 |
| 新邮件到 AI 结果就绪有延迟 | 产品文案明确「AI 摘要生成中」,WS 推送局部刷新,邮件本体不受影响 |
| 邮件服务商风控(频繁 IMAP 登录) | 复用长连接、退避重试、按服务商配置同步节拍 |
| 钓鱼识别误报影响正常邮件 | 警示仅为提示不拦截,误报可反馈,规则保守 |
